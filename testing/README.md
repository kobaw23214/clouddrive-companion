# PNA / LNA 浏览器拦截验证工具

验证现场浏览器是否拦截「公网 HTTP 页面 → 本地伴侣 (localhost)」请求，
以及写入企业策略注册表后是否能放行。对应三种现场情况：

| 情况 | 默认（未写注册表） | 写注册表后 | 结论 |
|------|------|------|------|
| 1 | 未拦截 (PASS) | 无需写 | 该版本不拦，直接可用 |
| 2 | 被拦截 (BLOCKED) | 未拦截 (PASS) | 策略有效，写注册表即可 |
| 3 | 被拦截 (BLOCKED) | 仍被拦截 (BLOCKED) | 策略无效，需另想办法 |

---

## 文件清单

| 文件 | 作用 |
|------|------|
| `pna-test.html` | 一键检测页面，出可视化结论 + 可下载 JSON 报告 |
| `serve.py` | 纯标准库静态托管脚本（兼容 Python 2.7 / 3.x），把页面挂到公网 |
| `apply-policy.bat` | 写入 Chrome/Edge 放行策略（管理员运行） |
| `clear-policy.bat` | 清除放行策略（管理员运行，用于测默认行为） |

> 本地探测端点 `/pna-probe` 已内置在 Go 伴侣客户端中（`internal/server/pna_probe.go`），
> 客户端启动后自动开启，无需单独部署。

---

## 前置：确认探测端点已就绪

1. 现场机器运行「网盘伴侣」客户端。
   - 测试页会**自动检测**客户端是否在运行；若未运行，会通过 `my-clouddrive://` 协议**自动唤起**
     并等待最多 6 秒（逻辑与生产页 `UploadComponent.vue` 一致），所以多数情况无需手动启动。
   - 唤起依赖客户端安装时注册的 URI 协议（`HKEY_CLASSES_ROOT\my-clouddrive`）。
2. 浏览器新标签直接打开 `http://localhost:34567/pna-probe`，应看到一段 JSON
   （`{"ok":true,...}`）。这是 loopback→loopback，永远不会被拦，用于确认端点存活。
   - 打不开 → 先解决客户端/端口问题，否则检测会把"端点没起"误判成"被拦截"。

> 关于客户端状态判定：测试页用 `/ping` 检测客户端。注意 ping 本身也是「公网→loopback」，
> 同样可能被 PNA 拦。所以"ping 不通"会显示为 **未确认（unknown）**，而不是武断地判为"未运行"——
> 这种情况下请用上面第 2 步的"直开 JSON"来确认客户端到底在不在。

---

## 第一步：把测试页挂到公网

把 `serve.py` 和 `pna-test.html` 一起拷到公网 Linux 服务器同一目录，执行：

```bash
python serve.py 8002          # 端口按需，建议复用现场真实业务端口段
# 或 python3 serve.py 8002
```

脚本会打印可访问地址。**关键：现场浏览器必须通过公网 IP 访问这个页面**
（如 `http://116.78.219.26:8002/pna-test.html`），
**不要用 localhost 打开测试页**，否则变成 loopback→loopback，结果无效（页面会红字警告）。

> 没有公网服务器时，也可在局域网另一台机器跑，用局域网 IP（192.168.x.x）访问，
> 局域网 IP 属 private 空间，打 loopback 同样会触发 PNA，可用于检测。

---

## 第二步：测「默认行为」（写注册表前）

1. 管理员运行 `clear-policy.bat`，清掉可能存在的旧策略。
2. **完全关闭并重启浏览器**（关掉所有窗口，策略/PNA 状态需重启刷新）。
3. 打开测试页（公网 IP），点「一键检测」。
4. 记录结论：
   - `✓ 未被拦截 (PASS)` → 属于**情况1**，这台/这个版本不用管。
   - `✗ 被拦截 (BLOCKED)` → 进入第三步验证策略是否有效。
   - `△ 非PNA：CORS问题` → 不是 PNA 问题，是探测端点 CORS 头异常，需排查端点。
   - `⚠ 检测无效` → 你用 localhost 打开了测试页，换公网 IP 重来。

---

## 第三步：测「写注册表后」（仅对被拦截的机器做）

1. 打开 `apply-policy.bat`，把里面的 `ALLOW_ORIGIN` 改成现场真实页面源
   （协议+IP+端口，如 `http://116.78.219.26:8002`），保存。
2. 管理员运行 `apply-policy.bat`。
3. 打开 `chrome://policy`（或 `edge://policy`），确认对应策略已出现且 Status=OK。
   - 策略**没出现** → 浏览器没读到策略（可能非受管理版本/路径问题），偏向**情况3 的子类**。
4. **完全重启浏览器**，再打开测试页点「一键检测」。
   - `✓ 未被拦截` → **情况2**：策略有效，现场写注册表即可解决。
   - `✗ 仍被拦截` → **情况3**：策略对该版本无效，需走其他方案（HTTPS / Wails 窗口 / 通信反转）。

---

## 第四步：收集报告

每次检测后，页面底部可「复制报告」或「下载报告 (.json)」。
报告含：浏览器名、版本号、地址空间、安全上下文、三项探测结果、最终结论。

把不同机器/版本的报告汇总，即可得到你要的产出：
**「哪些 Chrome 版本属于情况 1 / 2 / 3」**。

---

## 检测原理（为什么结论可信）

页面对本地端点做了三层探测，组合判定，避免误判：

1. **基线探测**：先请求页面自身，确认网络与 fetch 本身可用。
2. **CORS 探测** (`mode: cors`)：能读到 JSON = 完全通过（未拦截）。
3. **no-cors 探测** (`mode: no-cors`)：用于区分两种失败——
   - cors 失败但 no-cors 成功 = 请求其实**到达了**服务端，只是 CORS 头问题（**非 PNA**）。
   - cors 与 no-cors **都失败** = 请求在浏览器侧就被毙了 = **PNA 拦截**（前提是端点确实在运行）。

探测端点 `/pna-probe` 已回齐 `Access-Control-Allow-Origin`、
`Access-Control-Allow-Private-Network: true` 等头，
把"服务端缺头"这个干扰因素排除，使唯一变量只剩"浏览器是否拦截"。

---

## 注意事项

- 策略修改后**必须完全重启浏览器**，仅刷新页面不生效。
- `HKLM` 为全机策略；若现场用户无管理员权限或浏览器非受管理版本，
  策略可能不被读取，这本身就是「情况3」的一种表现，用 `chrome://policy` 可佐证。
- 旧策略 `InsecurePrivateNetworkRequestsAllowedForUrls` 在较新版本（如 Edge 137+）已废弃，
  故脚本同时写入新策略 `LocalNetworkAccessAllowedForUrls`，覆盖新旧版本。
